## 2. 구성요소 역할

| 컴포넌트 | 실행 위치 | 사용 파일 / 서비스 | 역할 |
|---|---|---|---|
| 브라우저 | Windows | `templates/sync.html`, `async.html` | 이미지 업로드, 결과 표시, 비동기 상태 폴링(1초 간격) |
| FastAPI | WSL `.venv` (uvicorn, 127.0.0.1:8000) | `main.py`, `ai/router_sync.py`, `router_async.py`, `router_web.py` | 요청 검증(5MB·형식), 동기 추론, 비동기 접수, 상태 조회 |
| ResNet18 | **서버와 Worker 각각** 프로세스 메모리 | `ai/hf_model.py`, `ai/services.py`, `artifacts/beans_resnet18/` | 이미지 분류. 프로세스별 첫 요청 때 로딩 후 재사용(`lru_cache`) |
| Redis 캐시 | Docker, DB 1 | `ai/cache_service.py` | 이미지 SHA-256 + 모델 경로 키로 결과 600초 재사용 |
| Redis 브로커 | Docker, DB 2 | `ai/celery_app.py` | Celery 작업 메시지 전달 |
| Redis 결과 백엔드 | Docker, DB 3 | `ai/celery_app.py` | Celery 작업 반환값 저장 (API는 사용하지 않음) |
| PostgreSQL | Docker | `ai/database.py`, `ai/models.py` | 비동기 작업 상태·결과(`image_jobs`) |
| Celery Worker | WSL `.venv` 별도 터미널 | `ai/tasks.py` | 비동기 추론 및 DB 갱신 |
| 업로드 저장소 | WSL 파일시스템 | `media/jobs/<uuid>.bin` | 비동기 원본 이미지 (DB에는 경로만 저장) |

## 3. 실행 환경

| 항목 | 값 |
|---|---|
| 운영체제 | Windows + WSL2 Ubuntu 26.04.1 LTS |
| Python | 3.11.17 (pyenv) + `.venv` |
| Docker | Docker Desktop 4.97.0, Engine 29.9.2, Compose v5.6.1 (WSL integration) |
| Docker 서비스 | `redis:7.4-alpine` (127.0.0.1:6379), `postgres:17-alpine` (127.0.0.1:5432) |
| 서버 프로세스 | `uvicorn main:app --host 127.0.0.1 --port 8000` |
| 워커 프로세스 | `celery -A ai.celery_app:celery_app worker --pool=solo --concurrency=1` |
| 모델 경로 | `.env` → `MODEL_PATH=artifacts/beans_resnet18` (Head-only 30 epoch, Val 0.9549) |
| 학습 장치 | GPU — NVIDIA GeForce RTX 3060 12GB (`torch 2.15.0+cu132`) |
| 추론(서빙) 장치 | **CPU** — `hf_model.py`의 `device=-1` 고정 (Worker 로그 `Device set to use cpu`) |

**실행 방식 선택:** 02 문서는 `web`·`worker`까지 Docker로 실행하는 방식을 제시하지만, 평가가이드 기준에 맞춰 **Redis·PostgreSQL만 Docker**로 실행하고 FastAPI·Celery는 WSL 가상환경에서 실행하였다 (`docker compose up -d redis postgres`). 이 경우 DB·Redis 주소는 `ai/config.py`의 기본값(`127.0.0.1`)을 사용하며, compose가 두 포트를 `127.0.0.1`로 공개한다.

## 4. 구조 검증 결과 (실제 관찰)

| 경로 | 흐름 | 관찰 근거 |
|---|---|---|
| 동기 | 브라우저 → FastAPI → Redis 캐시(MISS) → ResNet18 → FastAPI → 브라우저 | 응답 `cache_hit: false`, `inference_ms: 25.29` |
| 동기 (HIT) | 브라우저 → FastAPI → Redis 캐시(HIT) → 브라우저 | 응답 `cache_hit: true`, `inference_ms: null` |
| 비동기 | 브라우저 → FastAPI → `media/jobs` 저장 → PostgreSQL(queued) → Redis 브로커 → Worker → Redis 캐시/ResNet18 → PostgreSQL(done) → 브라우저 폴링 | Worker 로그 `Connected to redis://...:6379/2`, `Task ai.classify_job[...] succeeded`, 상태 조회 `done` |
| 캐시 공유 | 동기로 저장한 캐시를 비동기 Worker가 재사용 | job 4·6: `cache_hit: true` (동기 결과와 동일 점수) |

**설계상 유의점**
1. **모델이 두 프로세스에 따로 로드된다.** 서버와 Worker가 각각 첫 요청 때 모델을 불러오며(약 3.4초), 메모리도 두 배 사용한다.
2. **동기 요청은 `image_jobs`에 기록되지 않는다.** DB에는 비동기 작업만 남는다.
3. **Redis 캐시와 브로커는 같은 Redis 서버의 다른 DB 번호**를 쓴다. Redis가 멈추면 캐시와 큐가 함께 멈춘다. 단 캐시는 `cache_service.py`의 폴백으로 추론을 계속하지만, 비동기 접수는 503을 반환한다.
4. **모델 경로를 바꾸면 서버와 Worker를 모두 재시작해야 한다** (`lru_cache`로 이전 모델을 계속 사용).
