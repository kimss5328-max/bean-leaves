### 2-1. 재측정 (재현성 확인)

같은 조건으로 한 번 더 측정하였다 (`--output reports/data/timings_capture.csv`, 캡처 `evidence/measure_timings.png`).

| 항목 | 1차 측정 | 2차 측정 | 차이 |
|---|---:|---:|---:|
| 동기 MISS HTTP | 24.34 | 26.79 | +2.45 |
| 동기 HIT HTTP | 2.27 | 2.07 | -0.20 |
| 비동기 MISS 접수 | 9.96 | 9.01 | -0.95 |
| 비동기 MISS 최종 확인 | 214.27 | 220.82 | +6.55 |
| 비동기 HIT 최종 확인 | 211.99 | 220.39 | +8.40 |
| 추론 (서버 / Worker) | 19.90 / 17.86 | 20.40 / 17.78 | +0.50 / -0.08 |
| HTTP 응답 감소율 | 59.08% | 66.37% | +7.29%p |

- 두 측정의 **경향이 같다**: 비동기 접수가 동기보다 빠르고, 결과 확인은 약 190~195 ms 늦으며, 캐시 HIT은 동기 응답을 약 90% 줄인다.
- 감소율이 59%와 66%로 다른 것은 **값이 작아(수 ms) 몇 ms의 변동에도 비율이 크게 흔들리기** 때문이다. 감소율은 "약 60~66%"로 범위로 해석한다.
- 2차 측정의 워밍업은 서버·Worker 모두 이미 모델이 로드된 상태였다 (동기 29.31 ms, 비동기 완료 226.76 ms).
- 주의: `timings_summary.json`은 2차 측정 결과로 덮어써졌다. 1차 원본은 `timings.csv`, 2차 원본은 `timings_capture.csv`이다.

## 3. 계산

```text
HTTP 응답시간 감소율 (동기 MISS 대비 비동기 접수) = (24.34 - 9.96) / 24.34 × 100 = 59.08%
비동기 결과 확인 지연 (MISS)                     = 214.27 - 24.34                = 189.93 ms
캐시 효과 (동기)                                 = (24.34 - 2.27) / 24.34 × 100  = 90.67%
동기 MISS의 추론 외 처리 시간                     = 24.34 - 19.90                 = 4.44 ms
```

## 4. 결과 해석

1. **비동기 접수는 동기 응답보다 59.08% 빠르게 반환되었다** (24.34 → 9.96 ms). 이는 **추론이 빨라진 것이 아니라**, 요청 스레드가 추론을 기다리지 않고 작업만 접수한 효과이다. 추론 시간 자체는 서버(19.90 ms)와 Worker(17.86 ms)가 비슷하다.
2. **결과를 받기까지는 비동기가 약 190 ms 더 걸렸다** (214.27 대 24.34 ms). 큐 전달·Worker 처리·DB 갱신·상태 조회가 추가되기 때문이다.
3. **이 환경에서는 비동기의 이점이 작다.** CPU 추론이 약 20 ms로 매우 빨라서, 접수로 절약한 시간은 약 14 ms인 반면 결과 확인은 약 190 ms 늦어졌다. 비동기 구조는 **추론이 오래 걸리거나(대형 모델·대용량 이미지) 동시 요청이 많을 때** 서버가 막히지 않게 하는 데 의미가 있다. 이번 측정은 요청을 한 번에 하나씩 보냈으므로 동시성 효과는 측정하지 않았다.
4. **캐시 HIT은 동기 응답을 90.67% 줄였다** (24.34 → 2.27 ms). `inference_ms = null`은 추론을 생략했다는 뜻이며 0 ms가 아니다.
5. **비동기에서는 캐시 효과가 거의 보이지 않았다** (최종 확인 214.27 대 211.99 ms). Worker 처리가 첫 상태 조회(0.2초) 전에 끝나서, 최종 확인 시간이 **폴링 간격에 의해 결정**되었기 때문이다. 비동기의 실제 처리 시간 차이를 재려면 폴링 간격을 줄여야 한다 (예: `--poll 0.02`).
6. **각 프로세스의 첫 요청은 약 3.6초**가 걸린다 (모델 로딩). 서비스 시작 직후의 첫 사용자는 이 지연을 겪는다. 시작 시 미리 모델을 불러오는 워밍업이 개선 방안이다 (미구현).

## 5. 사전 관찰 (반복 측정 전, 참고용)

수동 실행에서 관찰한 단일 값이다. **조건이 통제되지 않았으므로 비교 근거로 쓰지 않는다.**

| 관찰 | 값 | 해석 |
|---|---:|---|
| 동기 MISS `inference_ms` | 25.29 ms | 모델이 이미 로드된 상태의 CPU 추론 시간 |
| 서버 첫 추론 `inference_ms` | 3,420.62 ms | **모델 로딩 포함** |
| Worker 첫 추론 `inference_ms` | 3,442.73 / 3,505.12 ms | **모델 로딩 포함** (프로세스 시작 후 첫 작업) |
| Worker 첫 작업 처리 시간 | 3.48 s | Celery 로그 `succeeded in` |
| 비동기 접수 (웹 화면) | 107 / 113 ms | 브라우저 측정 |
| 비동기 전체 (웹 화면, HIT) | 1,135 ms | 대부분 **화면의 1초 폴링 간격** |
| 비동기 전체 (웹 화면, MISS·첫 추론) | 4,155 ms | 모델 로딩 + 폴링 간격 |

**측정 방법상의 발견:** `services.py`는 시간 측정을 시작한 **뒤에** 모델을 처음 불러온다. 따라서 프로세스의 첫 요청 `inference_ms`에는 약 3.4초의 모델 로딩 시간이 섞인다. 워밍업 제외가 반드시 필요한 이유이다.

## 6. (참고) 평가가이드 문장 틀 — 4장에 반영 완료

평가가이드 기준 문장 틀:
- 비동기 접수 HTTP 응답은 동기 결과 응답보다 `[  ]%` 빠르게 반환되었다.
- 이는 **모델 추론이 빨라졌다는 뜻이 아니며**, 접수와 실제 처리를 분리한 효과이다.
- 결과를 확인하기까지의 시간은 비동기가 `[  ] ms` 더 길었다 (큐 대기·폴링 간격 포함).
- 캐시 HIT은 모델 추론을 생략하여 동기 응답을 `[  ]%` 단축하였다. `inference_ms=null`은 추론을 생략했다는 뜻이다.
- 서버와 Worker는 각각 모델을 따로 로드하므로, 각 프로세스의 첫 요청은 약 3.4초가 더 걸린다.
