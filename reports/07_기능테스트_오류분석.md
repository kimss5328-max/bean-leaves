## 3. 오류 이력 — 프로젝트 실행 (01 단계)

| 오류 ID | 현상 (실제 메시지) | 원인 | 조치 | 재검증 결과 |
|---|---|---|---|---|
| E-01 | `pyenv: python: command not found` | pyenv에 3.11.17이 설치되어 있으나 현재 폴더에서 쓸 버전이 지정되지 않음 | `pyenv local 3.11.17` | `python --version` → 3.11.17 |
| E-02 | 프로젝트 폴더가 `~/fastapi_resnet18/fastapi_resnet18`로 중첩 | 이미 같은 이름 폴더 안에서 생성 명령 실행 | venv 생성 전에 한 단계 위로 이동 | `~/fastapi_resnet18`에서 실행 |
| E-03 | `uvicorn` 실행 시 `ModuleNotFoundError: No module named 'PIL'` | 패키지 미설치 (`requirements.txt` 설치 전) | requirements 설치 | 설치 후 `uvicorn` 정상 기동, 동기 API 200 |
| E-04 | `ERROR: Could not open requirements file` | 현재 폴더에 `requirements.txt` 없음 | 01 문서 3장의 목록으로 파일 확보 후 설치 | 설치 완료 |
| E-05 | `Command 'pytest' not found` → `pip install python3-pytest` 시도 | `python3-pytest`는 apt(시스템) 패키지 이름. pip 이름은 `pytest`. apt로 설치하면 venv 밖에 설치됨 | `python -m pip install pytest httpx`, `python -m pytest` | `python -m pytest` 실행 가능 (02 모의 테스트 4 passed) |
| E-06 | `curl: (26) Failed to open/read local data from file/application` | `${TEST_IMAGE}` 변수가 비어 있음 (터미널 재시작 시 변수 소멸) | 이미지 경로를 직접 지정 | 경로 직접 지정 후 동기 응답 정상 |

**교훈**
- pip 패키지는 `python -m pip`로 설치하면 현재 venv에 확실히 설치된다.
- `requirements.txt` 설치가 중간에 실패하면 pip은 전체 설치를 취소하므로, 여러 모듈이 연쇄적으로 없다고 나온다.

## 3-2. 오류 이력 — 02 단계 (비동기·Docker)

| 오류 ID | 현상 (실제 메시지) | 원인 | 조치 | 재검증 결과 |
|---|---|---|---|---|
| E-07 | `cp: cannot stat '.env.example'` | 02용 `.env.example` 미작성 | 02 문서 7장 내용으로 생성 | 생성 |
| E-08 | `The command 'docker' could not be found in this WSL 2 distro` | Docker Desktop은 설치되어 있으나 실행되지 않음 (`wsl -l -v`에서 `docker-desktop` Stopped) | Docker Desktop 실행, WSL integration에서 기본 배포판 `Ubuntu` 활성화 | `docker version` Client·Server 확인 |
| E-09 | `pg_isready` → `no response` | 컨테이너 시작 1초 후라 PostgreSQL 초기화 중 (`health: starting`) | 수 초 대기 후 재확인 | accepting connections |
| E-10 | 같은 이미지로 알고 보낸 요청이 Worker(job 1)에서는 healthy 0.47, 서버에서는 angular_leaf_spot 0.84~0.94 | **원인: 이미지 혼동 (확인됨).** 모델 경로 정리(3 epoch → 30 epoch) 전후에 시작된 프로세스가 섞였을 가능성이 가장 높음. `model_id`는 경로 문자열만 기록하므로 DB로는 구분 불가 | 캐시(DB 1)를 비운 뒤 같은 이미지로 서버·Worker 각각 직접 추론 비교 | 서버·Worker 모두 0.8439902로 **일치** (T-16). job 1·3·7의 저장 이미지 SHA-256이 모두 달라(`24776b80…`, `ad6a8ff2…`, `efc1a74c…`) **서로 다른 이미지였음을 확인**. 모델·프로세스 문제가 아니었다. |
| E-12 | 성능 측정 중 `RuntimeError: job 19가 60초 안에 끝나지 않았습니다` | Celery Worker 프로세스가 종료되어 있었음. 상태 조회 결과 job 19는 `queued`, `top1` null | Worker 재시작 (`celery -A ai.celery_app:celery_app worker ...`) | 재시작 직후 Redis 브로커에 남아 있던 job 19를 자동으로 받아 처리(`succeeded in 3.39s`, 모델 로딩 포함) → done. **작업이 유실되지 않음** |
| E-11 | 첫 요청 `inference_ms` 약 3,400~3,500ms | `services.py`가 시간 측정 시작 후 모델을 처음 로딩 | 성능 측정 시 워밍업 요청을 보내고 비교에서 제외 | `measure_timings.py`에 반영 |

**교훈**
- Worker가 꺼져 있어도 FastAPI는 202로 접수하므로 **사용자는 실패를 바로 알 수 없다.** 작업이 `queued`에 오래 머무르면 Worker 상태부터 확인한다. 반대로 작업은 Redis 브로커에 남아 있어 Worker를 다시 켜면 이어서 처리된다(E-12).
- 모델 파일을 교체한 뒤에는 **서버와 Worker를 모두 재시작**한다. `lru_cache`로 이전 모델을 메모리에 계속 들고 있을 수 있다.
- 결과가 다르다고 판단하기 전에 **입력 이미지가 같은지 해시로 먼저 확인**한다. E-10은 이 확인으로 해결되었다.
- 캐시가 켜진 상태에서는 "같은 결과"가 "같은 추론"을 뜻하지 않는다. 프로세스별 추론을 비교하려면 **캐시를 비우고** `cache_hit: false`를 확인해야 한다.
